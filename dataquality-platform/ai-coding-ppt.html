01 · 背景与痛点

为什么需要数据质量检测平台？

😤 算法工程师的日常痛点

📁

数据格式混乱

JSON / JSONL / Excel / ShareGPT / Alpaca / CSV...
每种格式字段名都不一样，训练脚本适配成本高

🐛

数据质量参差不齐

乱码、截断、异常字符、空值、重复数据...
清洗全靠一堆零散的脚本，无法复用

📊

效果难以量化

数据清洗前后的质量变化没有量化指标
模型效果差也不知道问题出在哪

💡 核心问题链

GIGO Principle — Garbage In, Garbage Out
数据采集 → 格式转换 → 数据清洗 → 微调训练 → 模型效果
混乱的源头___________________
数据质量差，模型怎么调都没用

解决方案

🔍 质量检测
→
📋 问题定位
→
✅ 清洗过滤
→
🚀 训练上线

03 · 核心技术实现

Dingo 引擎深度集成

⚙️ 核心执行流程

# engine.py — 核心集成层 def build_input_args(ds_config, rule_configs): dataset_args = DatasetArgs() # 根据数据源类型构建配置 if ds_type == "local_file": dataset_args.source = "local" dataset_args.format = fmt elif ds_type in DB_TYPES: dataset_args.source = "sql" dataset_args.sql_config = DatasetSqlArgs( dialect=dialect_map[ds_type], ...) # 自定义规则 → RulePatternSearch for rc in rule_configs: if rule_type == "pattern": eval_config = EvaluatorRuleArgs( pattern="|".join(patterns)) evals.append( EvalPiplineConfig( name="RulePatternSearch", config=eval_config)) return InputArgs(..., evaluator=evaluator) async def run_evaluation_task(...): executor = Executor.exec_map["local"] result = executor.execute()

🔑 源码关键路径

分析
数据从数据库到规则评估的完整链路
发现
规则假设 content 为 str，非文本字段需转换
集成
自定义规则通过 RulePatternSearch 执行

📦 数据类型处理策略

SQL → Python 原始类型保留（int/float/str/datetime）
Converter → 直接透传，不做类型转换
规则层 → ⚠️ 假设 content 为 str，可能对数值类型报错
💡 发现的问题

dingo 设计面向 LLM 训练文本数据，所有规则都假设 input_data.content 是字符串类型。 数据库 int/float/datetime 字段直接透传，会导致规则执行报错。
